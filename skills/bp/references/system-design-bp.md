# System Design Validation

Evaluate system architecture and design decisions against fundamental engineering principles.
Surface any violations and explain the trade-offs.

## Principles

### Idempotency

Running the same operation multiple times must produce the same result as running it once.

Check for:

- Operations that mutate state without idempotency guards
- Side effects that compound on repeated execution
- Missing deduplication or at-least-once delivery handling

### Distributed Systems

Prefer observable systems. Observability consists of:

- Logs: levelled, timestamped, with modules/components/threads/processes/, maybe in json format
- Metrics: numeric measurements over time, with dimensions/tags for filtering and aggregation
- Traces: end-to-end request flow across services, with timing and metadata

Use trace id that is generated at the edge (start) of request and propagated through all services.
For example it could be generated on the client side and injected into http header, or generated by the edge service (e.g. API gateway) and injected into downstream calls.

## DevOps Tools to keep in mind

- Docker containers: immutable, self-contained environments for running applications
- Kubernetes: orchestration platform for managing containerized applications at scale
- Service discovery: dynamic registration and discovery of services in a distributed system (for example, DNS-based)
- Load balancing: distributing incoming traffic across multiple instances of a service
- Health checks: monitoring the health of services and automatically restarting or replacing unhealthy instances
- Observability tools: centralized logging, metrics, and tracing systems for incident response and performance monitoring
- CI/CD pipelines: automated workflows for building, testing, and deploying applications
- Infrastructure as Code (IaC): managing infrastructure using code and automation tools (e.g. Terraform, CloudFormation)
- Secret management: secure storage and access of sensitive information (e.g. HashiCorp Vault, AWS Secrets Manager). Secrets are injected into applications at runtime - never hardcoded in git, never touch the disk, never print in logs and rotate regularly/automatically.
- Disaster recovery: define RPO (Recovery Point Objective) and RTO (Recovery Time Objective) which determine how much data loss is acceptable and how quickly the system must be restored after a failure.
